## 1. 検討の流れ

1. `domain-model.md` の細部（TBD項目）を詰める前に、一度アプリの大きなテーマ（犬育成×ゲーム要素）から再検討したいという要望
2. 4方向の育成コンセプト案を提示（A: 育成×日課型 / B: 育成×コレクション型 / C: 育成×探索/バトル型 / D: 育成×公開/SNS型）
3. Aを軸に採用、B・Dは後から追加するレイヤーという位置付けに

6. MVPスコープを確定

## 2. 決定事項

### コンセプトの軸
- **A. 育成×日課型**（毎日のお世話でステータス変動→レベルアップ）を採用
- B（コレクション）・D（公開/SNS）はMVP後に追加検討。C（探索/バトル）はスコープが重いため見送り

### フロントエンド/バックエンド分離のタイミング
- 3案（①最初から分離／②MVPまでLivewire→後から分離／③このアプリでは分離しない）を検討
- **②を採用**。理由: Service層を呼び出し元非依存に設計しておけば分離コストを抑えられる（既存の設計方針と整合）、ゲーム仕様確定とアーキテクチャ変更を同時にやらずに済む
- リスク（「後でやる」が実現しない）への対策として、`docs/mvp.md` に「MVP完了の定義」を明文化し、分離着手のトリガーとした

### レスポンシブ対応
- 本格的なモバイルUXは分離のタイミングで検討
- ただしTailwindのレスポンシブユーティリティ自体はMVPから使う（フロントエンド分離とレスポンシブ対応は別の関心事、という整理）

### ステータス減衰の計算方式
- 「都度計算方式」（画面表示時に `last_interacted_at` からの経過時間で計算）に決定
- Laravel Schedulerによるバッチ処理はMVP後の学習用拡張ポイントとして保留

### MVPスコープ
- ユーザー登録/ログイン、相棒犬登録（1人1匹）、ステータス表示、お世話アクション3種、レベルアップ、時間経過による減衰
- 詳細・後回し項目は `docs/mvp.md` を参照
