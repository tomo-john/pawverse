# MVP要件 — pawverse

大テーマ「犬をテーマにしたアプリ + ゲーム要素」のうち、最初に作り切るMVPの範囲を定義する。
ドメインの詳細は [`docs/domain-model.md`](./domain-model.md) を参照。

---

## 1. コンセプトの軸

犬育成の方向性として、以下4案を検討した結果、**「A. 育成×日課型」を軸に据える**ことに決定。

| 案 | 概要 | 採用状況 |
|---|---|---|
| A. 育成×日課型 | 毎日のお世話でステータスが変動し、レベルアップしていく王道たまごっち系 | **MVPの軸として採用** |
| B. 育成×コレクション型 | 遊ぶことでアイテムがドロップし、集める・着飾る | MVP後に追加検討 |
| C. 育成×探索/バトル型 | エリア解放・ランダムイベント | 今回は見送り（スコープが重い） |
| D. 育成×公開/SNS型 | 犬を公開して他ユーザーが見にいく | MVP後に追加検討 |

## 2. アーキテクチャ方針

### フロントエンド/バックエンド分離のタイミング

3案を検討し、**案2（MVPまでLivewireで進め、後から分離する）を採用**。

- 案1（最初から分離）: ゲーム仕様の確定とアーキテクチャ分離という2つの不確実性を同時に抱えるため見送り
- 案3（このアプリでは分離しない）: 分離を学ぶ機会として自然なテーマなので見送り
- **案2を採用した理由**:
  - Service層を「呼び出し元（Livewire/APIコントローラ）を意識しない」設計にしておけば、後から分離するコストを最小化できる（`docs/domain-model.md` の設計方針と整合）
  - 「ゲームの中身を固める」→「それを分離する」と課題を直列で処理できる
  - モノリス→分離という進化は実務でも頻出パターンで、ポートフォリオとしても語れる

**リスクと対策**: 「後で分離する、と言いつつやらない」が最大の落とし穴。対策として本ドキュメントの「4. MVP完了の定義」を分離着手のトリガーとして明文化する。

### レスポンシブ対応

- 本格的なモバイルUX（タッチ操作最適化、専用ナビゲーション等）は**分離のタイミングで検討**する
- ただし、Tailwindのレスポンシブユーティリティ（`md:` 等）を使うこと自体はコストがほぼゼロなので、**MVPの時点から自然に使い、極端に崩れない程度は担保する**
  - 「フロントエンド分離」と「レスポンシブ対応」は別の関心事であるため、分離のタイミングにまとめて先送りしない

### UI/コンポーネントについて

- MVPでもLivewire/UIの作り込みとコンポーネント化は意識する（将来分離してもUIの構造的な設計思想は活きるため）

## 3. MVPに含める機能

1. ユーザー登録・ログイン（既存のLaravel Breeze/Fortifyをそのまま流用）
2. 相棒犬の登録（1人1匹、名前・性格などの初期設定）
3. 犬の「家」画面（現在のステータス表示: レベル・経験値・Happy・HP）
4. お世話アクション最低3種（例: 餌をあげる／遊ぶ／なでる）→ ステータス変化 + `DogGrowthEvent` 記録
5. レベルアップの仕組み（経験値が閾値を超えたら上がる。上がるほど必要経験値が増える）
6. 時間経過によるステータス減衰（放置系要素。都度計算方式、`docs/domain-model.md` 参照）

## 4. MVP完了の定義

上記1〜6が一通り動作した時点でMVP完了とする。完了したら、フロントエンド/バックエンド分離フェーズの検討に着手する。

## 5. MVPでは後回しにするもの

- 複数飼育の実運用（上限チェックなど。モデルは `User has many Dog` のままでOK）
- ミニゲーム、アイテム/コレクション（B案）
- 公開/SNS機能（D案）
- 外部API連携・自前API化（分離フェーズで対応）
- 本格的なモバイルUX
- リアル犬の活動記録連携（RealDog。`docs/domain-model.md` の将来の拡張ポイント参照）
